# Decision 003: Управление зависимостями фронт ↔ бэк ↔ аналитика

## Дилемма
Типичная цепочка: аналитика → дизайн → фронт/бэк → QA.
Если аналитика задерживает ТЗ, фронт и бэк простаивают.
Если бэк меняет API, фронт переделывает.
Вариант A: ждать готовности аналитики — медленно.
Вариант B: параллельная работа с риском переделок — быстрее, но дороже.

## Критерий
Стоимость переделки vs стоимость простоя.

## Решение
Ввёл реестр зависимостей + контракт API как gate:
- Аналитика отдаёт ТЗ в виде user stories + acceptance criteria.
- Бэк фиксирует OpenAPI-контракт до старта фронта.
- Фронт начинает только после утверждённого контракта.
- QA получает acceptance criteria как основу тест-плана.

## Результат
- Переделки фронта из-за изменения API: −50%.
- Простой фронта из-за ожидания аналитики: сократился.
- Цена: +2 дня на этап контракта API.
- QA получил тест-план раньше.
